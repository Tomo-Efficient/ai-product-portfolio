## 01 / 背景

求职者并不缺题。真正缺的是：**有人拿着我的简历，问我这里为什么这么做、这个数字怎么算、如果重来会改哪一步。**

作者此前用过一版开源面试 Demo。它能跑通对话，但题目来自固定题库，简历和 JD 只是装饰；反馈以鼓励为主，没有证据；练完也不沉淀。于是我决定重做整条训练链路，而不是换一个聊天界面。

## 02 / 我的判断

如果只能解决一个问题，先解决「题目是否来自我的简历和 JD」。这是它和通用 Chatbot 的分水岭。

围绕这个判断，我定了三条产品原则：

- **每道题有来源**：简历里的项目、指标、JD 里的能力项，至少能追溯到一个。
- **每条反馈有证据**：不写“再具体一点”，而是指出哪一句缺口径、哪一步没有讲决策。
- **每次练完能再练**：低分题进入个人题库，按 1 / 3 / 7 天复习。

## 03 / 产品结构

| 模块 | 解决的问题 | 关键设计 |
| --- | --- | --- |
| 简历解析 | 把 PDF / DOCX 变成结构化画像 | 自研 DOCX 解析；规则抽取教育、经历、指标、技能；给出解析质量分 |
| 岗位匹配 | 题目要贴目标岗位 | 岗位包 + 关键词覆盖 + 缺口提示，而不是泛泛的“匹配度” |
| 模拟面试 | 让追问像真实面试 | 三种人格；条件路由决定追问还是换题；每题最多 2 次追问 |
| 复盘报告 | 练完知道下一步改什么 | 五维评分、逐题证据、知识库引用、7 天行动清单、题库沉淀 |

## 04 / 关键设计

### 状态机，而不是一次 Prompt

面试不是“生成一段话”。一次作答要经过：评估 → 路由 → 追问 / 换题 / 收尾 → 生成回复。我把这条链路做成显式状态机：

```text
evaluate_answer → route → ask_question / wrap_up → END
```

是否追问由规则裁决：回答太短、缺少口径、专业深度不足或出现“大概、记不太清”时追问；明确说“不会”则不重复施压；整场追问有总预算，避免变成审讯。所有节点写入 trace，右侧实时可见。

### 检索是为了“有依据”，不是为了炫技

知识库只有 16 篇、题库 80 道，用 BM25 + 中文 bigram 就足够，而且完全可解释。出题时召回候选题目，复盘时召回知识库要点，报告里直接展示引用。

### 本地优先，模型可选

没有 API Key 也能完整跑通：出题、追问、五维评分、报告全部由本地规则引擎完成，并在 UI 上明确标注“规则评分”。配置模型后，追问和点评更自然；模型失败自动降级，不把产品可用性押在模型稳定性上。

## 05 / 结果与复盘

- 80 道题、16 篇教研知识、6 个岗位包、3 种面试官人格。
- 完成 **158 条测试用例**（功能 51 + 接口 55 + UI 30 + 后台/安全 8 + LLM/边界 14），发现 6 个缺陷并全部修复，无未关闭 P0/P1。
- 产品投入常态化使用，全套面试准备材料产出耗时缩短约 **40%**。

更重要的是，它让我把“AI 产品”拆成了可验证的几层：内容契约、状态机、检索依据、评分 rubric、降级策略。这些比“会写 Prompt”更难，也更能说明一个 AI 产品经理的判断。

## 06 / 如果继续

- 多场趋势对比：同一道题在三次练习里的结构、量化、深度变化。
- 语音作答与语速、口头禅分析。
- 把报告导出成可分享的复盘卡，支持教练点评。
- 评测集扩充到真实用户匿名样本，校准规则评分与模型评分的一致性。

> 这个项目是个人项目，不包含任何雇主的业务数据；演示数据为虚构候选人。
