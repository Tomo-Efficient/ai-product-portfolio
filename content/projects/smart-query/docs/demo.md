# 智能问数 Agent 演示脚本

> **这是方案演示，不是生产直播。** 页面数据为预置模拟数据，不含真实客户、保单或机构信息；SQL 不会发往真实数据库。生产系统属于招商金科内部项目，不能对外演示。数字仅用于讲清逻辑，不构成业务事实。

快照为 **2026-06-30**，所以「上个月」指 **2026 年 5 月**。演示角色：某业务条线经营分析岗，不写 SQL。

---

## 1. 演示前准备

- 页面有 3 个预置 Tab：**渠道保费环比**、**互联网退保率**、**件均保费趋势**。点击切换，不是自由输入。
- 演示页聚焦 SQL、evidence 与检查项；图表和安全沙盒在完整产品中，本文用讲解分支补足。
- 演示 SQL 用 `CURRENT_DATE` 和 PostgreSQL 语法简化；生产锚定数据截止日，用 Hive/Spark。
- 放大字号，SQL 默认折叠，讲检查项时再展开。

演示用三张表：`dws_policy_premium_di`（保单-月保费，`stat_date` 分区）、`dim_channel`（渠道）、`dim_risk`（险种）。口径：保费收入 = `SUM(premium)`，剔除退保与失效保单；退保率 = 退保件数 / 承保件数；件均保费 = 保费 / 保单件数，按 `policy_no` 去重。

## 2. 三分钟版

目标是让人记住三件事：**快、准、稳**。

| 时间 | 问题 / 操作 | 讲什么 | 屏幕 |
| --- | --- | --- | --- |
| 0:00—0:20 | 开场 | 「业务取数平均等 6 小时，真正写 SQL 只要十分钟，剩下都在排队和澄清。我要压掉的是这段等待。」 | 项目首页 |
| 0:20—0:40 | 说明定位 | 「B 端数据产品，不是聊天机器人。业务问数，系统生成 SQL，返回文字、数据和图；生产在内网，今天用模拟数据。」 | 模拟标识；3 个 Tab |
| 0:40—1:10 | 「近 7 天各险种的件均保费」 | 「单表 join 维表、按保单去重，走 few-shot 单轮改写。结果重疾 8,420 元、年金 6,150 元、医疗 1,980 元。」 | 路由 simple；3 行结果；去重校验 |
| 1:10—1:50 | 「上个月各渠道的保费收入环比」 | 「中等复杂度：两次聚合、join 渠道维表、两个月对比。先检索证据，再生成、校验，最后给表和结论。」 | 3.12 亿；4 个渠道；SQL；evidence |
| 1:50—2:20 | 展开检查项 | 「只读账号、AST 校验、自动 LIMIT、口径命中四项都过。写操作在 AST 层就被拒，手机号默认脱敏。」 | checks 四项 pass |
| 2:20—2:45 | 指标页 | 「灰度期答案正确率 85% 以上；系统链路从 6 小时到 30 秒级；接入 10+ 个真实 ETL 脚本、近千字段。」 | 评测摘要 |
| 2:45—3:00 | 收尾 | 「它不替代 BI，也不替代数据开发；把标准问题前置，复杂问题交回人。」 | 能力边界 |

**关键话术**

> 「『上个月』被归一化成明确区间；『保费收入』落到指标平台公式；渠道名来自维表。这三件事决定答案可不可信。」

> 「Prompt 里写『不要删表』没用。AST 拒绝写操作、只读账号、自动 LIMIT 和脱敏才有用。安全靠确定性，不靠模型自觉。」

## 3. 十分钟版

结构：问题—演示—机制—边界。

| 时间 | 场景 | 问题 / 操作 | 讲解重点 |
| --- | --- | --- | --- |
| 0:00—0:50 | 开场 | 不操作 | 6 小时基线；B 端定位；模拟数据声明；看一条链路 + 三条边界 |
| 0:50—2:40 | 渠道环比 | 「上个月各渠道的保费收入环比」 | 时间归一化；两次聚合；join 维表；3.12 亿；证据与 SQL |
| 2:40—3:40 | 简单查询 | 「近 7 天各险种的件均保费」 | 路由 simple；按保单去重；件均口径；结果表 |
| 3:40—5:10 | 退保率 | 「上季度互联网渠道的退保率是多少？」 | 4.7% vs 均值 3.9%；分母口径；件数口径；30 天内集中 |
| 5:10—6:40 | 追问归因 | 「按险种拆，看看是不是某类产品集中退保」 | 讲解分支；Agent Loop；相关不等于因果；边界 |
| 6:40—7:50 | 安全 | 展开 q1 checks；口头问「把表删了」「导出手机号」 | 只读；AST；LIMIT；脱敏；导出审批；审计 |
| 7:50—8:40 | SQL 与修复 | 展开 SQL / evidence | 4 条证据；Checker 四项；失败最多 2 轮 Repair |
| 8:40—9:30 | 评测 | 打开评测摘要 | 85% 的 execution accuracy；10+ ETL、近千字段；分母差异 |
| 9:30—10:00 | 收尾 | 能力边界 | 不替代 BI/数据开发；复杂归因有限；下一步 |

### 第 1 段：开场

> 「我在招商金科做智能问数 Agent。改造前一次临时分析平均 6 小时，瓶颈不是 SQL，是排队和澄清。目标是让业务在受控范围内自己拿到数。」

### 第 2 段：渠道环比（主问题）

点开「渠道保费环比」，系统先把「上个月」转成明确区间，再分别聚合本月与上月，join 渠道维表，算环比。

**结果（模拟，万元）**：

| 渠道 | 保费收入 | 环比 |
| --- | ---: | ---: |
| 个险代理人 | 12,840 | +8.4% |
| 银保渠道 | 9,620 | -2.1% |
| 互联网 | 5,480 | +21.6% |
| 经纪代理 | 3,260 | +3.2% |

> 「全渠道 3.12 亿元，环比 5.8%。互联网增速最快，银保小幅下滑，个险代理人仍是最大来源。这个结论和 SQL 的 GROUP BY 一一对应，不是模型编的。」

展开 evidence：指标公式「剔除退保与失效」、同义词、环比按自然月、`stat_date` 分区并关联 `dim_channel`。再看 SQL：两个 CTE、`NULLIF` 防除零、`LIMIT 100`。

**追问点**：为什么不一条 SQL 算两个月？先各自聚合再 join，避免两个月明细混在一起导致重复计数。

### 第 3 段：件均保费（简单查询）

点开「件均保费趋势」，路由 `simple`：join `dim_risk`，用 `SUM(premium) / COUNT(DISTINCT policy_no)` 算件均，按保单去重。

**结果**：重疾险 8,420 元（1,260 件）、年金险 6,150 元（840 件）、医疗险 1,980 元（3,420 件）。

> 「医疗险件均最低但件数最多，适合做交叉销售入口。这个结论不需要 Agent 多轮推理，单轮改写 + 去重校验就够了——简单问题用重方案是浪费。」

### 第 4 段：退保率（口径问题）

点开「互联网退保率」：上季度 4.7%，高于全渠道均值 3.9%，涉及 18,420 件保单，主要集中在投保后 30 天内。

> 「退保率有两个常见口径：退保件数 / 承保件数，或退保保费 / 期初有效保费。这两个数不能直接横比。页面展示的是件数口径，答案里必须写清楚。」

**钩子**：要保费口径就切换公式重算，而不是乘系数。口径由指标平台登记，不靠模型临场解释。

### 第 5 段：追问归因（讲解分支）

> 「如果继续问『为什么互联网退保率上升』，页面没有预置这张卡，我会用讲解说明 Agent 会怎么走：先拆退保率公式，再按险种、产品、投保时间下钻，最后给相关维度和待验证假设。」

> 「它只能告诉你哪些维度同时变化，不能证明因果。真要归因，需要业务假设、对照实验或保单级分析。说清边界，比给一个自信的错误结论更有价值。」

### 第 6 段：安全（看检查项，不真的攻击）

页面没有攻击输入框，直接展开 q1 的 checks：

- **只读账号**：使用 `analytics_ro`，写操作在数据库层也会失败。
- **AST 校验**：无写操作、无全表扫描；`DROP`/`DELETE` 在解析层拒绝。
- **自动 LIMIT**：SQL 带 `LIMIT 100`，护栏兜底。
- **口径命中**：保费收入、有效保单、环比三项与指标平台一致。

> 「如果现场问『把客户表删了』，AST 会拒绝，不会到数据库；问『导出所有手机号』，默认掩码，导出要走审批、水印和审计。安全不靠模型自觉。」

### 第 7 段：SQL 与修复

展开 SQL 和 evidence，讲三件事：证据如何约束表/字段；Checker 如何查 join、时间、聚合、权限；失败时 Repair 最多 2 轮，只做最小修复，不删业务过滤条件。

> 「注意演示 SQL 里的 `CURRENT_DATE` 是页面简化；生产会把相对时间锚定到数据截止日，避免跨月执行时结果漂移。」

### 第 8 段：评测与收尾

> 「85% 是 execution accuracy：SQL 结果与标准 SQL 一致才算对，不是文本相似。评测集双人标注，覆盖歧义、空结果、越权和脏数据。」

> 「6 小时到 30 秒，比的是流程等待和系统链路；90% 是自报端到端降幅，样本有限。三个数字必须带分母。」

> 「最重要的不是 Agent，而是语义层、评测和安全护栏。下一步把复杂归因做成可复用模板，而不是让 Agent 每次自由发挥。」

## 4. 可能被追问的问题与回答

**Q1：这是真实的生产系统吗？**

> 不是。生产系统在招商金科内网，代码和数据不能对外；这里是作品集交互演示，用模拟数据复现关键状态。

**Q2：85% 怎么算？会不会自说自话？**

> 用 execution accuracy：Agent SQL 结果与数据开发标注的标准结果一致才算对，允许浮点误差和排序差异。评测集双人标注、争议复核、按难度分层。85% 是灰度分布下的结果，长尾会低于均值。

**Q3：剩下 15% 错在哪？**

> 主要是 join 粒度放大（订单级 join 保单级导致金额翻倍）、口径选错（签单日/生效日、退保冲减）、时间边界错（分区、跨年、财年）。修复要补粒度说明、指标卡和分区规则，再跑回归。

**Q4：怎么防模型编表、编字段、编数字？**

> 检索只给候选资产；生成要求引用 `E*`；Checker 校验存在性与口径；Composer 只能引用结果集，百分比由代码算。没证据就澄清或拒答。AST 和只读账号是确定性兜底。

**Q5：行级权限怎么做？**

> 登录注入 `user_scope`，检索只召回授权资产；生成后护栏强制注入组织过滤；结果层列级脱敏；全链路审计。风险在组织映射质量，兼岗、代管要定期对账。

**Q6：为什么用 Claude Code 搭 Agent？**

> 它能快速把「拆解—工具调用—观察—反思」跑通，工具和 trace 直观，适合早期验证。产品化时保留同一套状态机，把模型和工具接到内部网关；它是搭建载体，不是交付形态。

**Q7：30 秒是真的吗？怎么又说是 90%？**

> 30 秒是系统链路 P50，不含业务复核；6 小时是原完整流程，含转译、排期、回传、复核，分母不同。90% 是业务自报的端到端降幅，样本有限。分开讲才经得起追问。

**Q8：业务不用怎么办？**

> 嵌入现有工作流，不要求新开工具；展示 SQL、口径、截止时间，建立信任；试点选高频痛点；答不了明确转人工。自助率是结果，不是上线指标。

**Q9：复杂归因到底能做什么？**

> 能拆公式、按维度下钻、找同时变化的因素、给待验证假设；不能证明因果、替代业务判断、覆盖长尾。把「相关」和「因果」分开写，是刻意设计。

**Q10：和 BI、开源 Text2SQL 的区别？**

> BI 解决已知问题的规模化展示，我们解决临时问题的自助入口；开源 Text2SQL 解决生成 SQL，我们解决企业在语义和权限约束下生成可信 SQL。差别不在模型，在语义层、检索、校验、评测和运营。

**Q11：口径变了或模型挂了怎么办？**

> 语义资产和指标定义版本化，变更走评审并触发回归；答案展示指标版本与数据截止时间。模型故障时按「缩小上下文重试 → 备用模型 → 指标模板 → BI/人工」降级，且不绕过权限、LIMIT、脱敏和审计。

**Q12：成本多少？**

> 按网关假设单价，简单约 1 分、中等 2 分、复杂 8—12 分；每天 300 次约 6.5 元/天、195 元/月。真正贵的是错误重试和多轮调用，路由、缓存、Repair 上限比换便宜模型更有效。
